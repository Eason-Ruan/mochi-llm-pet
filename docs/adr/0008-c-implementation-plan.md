# ADR-0008 · C 界面与工作段实现计划

Proposed · 2026-11-12 · 负责人 C，联调方 A、B、D

## 1. 背景与目标

C 负责动态界面（A5）和工作段管理（A7）。目前 M0 已提供 Qt 联调台、可嵌入界面样例、有状态工作段 mock、共享时钟、任务接口和事件回放，可以用于独立开发与联调。C 将在这些接口上实现可操作的工作面板、提醒卡片、专注计时和工作回顾，后续再与桌面小猫整合。

体验依据为仓库中的 [用户体验设计说明](../user-experience.md)，接口依据为 [GUI 与工作段契约](../contracts/gui-work.md)、[C 交接文档](../handoff/c-gui-work-sessions.md)及 [ADR-0007](0007-embedded-ui-surface.md)。本文描述拟采用的方案与交付顺序，状态为 Proposed，不代表相关功能已经实现。仓库体验说明标注了对应飞书链接，在线版本若有更新，需同步核对。

第一轮希望完成以下用户闭环：

- 用户填写工作目标和时长，开始一段专注；中途可以暂停、继续或提前结束。
- 工作段到期后显示结束提示，用户确认成果和下一步，再查看本轮回顾。
- 提醒到达时显示明确的事项与操作，支持完成、延后、修改和取消。
- 工作面板、提醒卡与联调台诊断页呈现同一份任务和工作段状态。
- 用户能查看系统估计的状态，设置有期限的纠正，并看到操作结果。

## 3. 技术方案与模块划分

### 3.1 复用现有 Qt 宿主

采用 Python / PyQt6，通过 `ui_surface` 工厂将 C 的 QWidget 嵌入「C 界面 · 实际展示」页。宿主继续负责 QApplication、服务线程、共享 Clock、快照发布和 queued gateway。C 的组件在 Qt 主线程运行；领域服务在宿主服务线程运行。

组件实现以下接口：

| 接口 | C 的职责 |
| --- | --- |
| `create_surface(*, context, parent)` | 创建组件、连接结果信号、初始化等待状态；收到服务快照后启用业务操作 |
| `render_snapshot(snapshot)` | 根据最新任务、工作段与观察帧更新视图，保留正在编辑的表单与选择项 |
| `show_reminder(command)` | 按交付 ID 创建或复用卡片，安排可见绘制后的回执处理 |
| `dismiss_reminder(task_id)` | 删除该任务的旧卡，停止相关回调并释放控件 |

界面经 `context.submit_action()` 提交 UiAction，通过 `context.result_received` 接收结果。快照是显示依据，服务返回结果是操作成功与否的依据。界面只保留输入草稿、选择项、待处理动作和控件映射，不维护第二份任务状态机或业务倒计时。

### 3.2 拟新增的 C 模块

以下路径是实现时拟采用的结构，本 ADR 不创建这些业务模块：

| 建议路径 | 职责 |
| --- | --- |
| `deskpet/c_ui/surface.py` | 组件入口、页面布局、快照分发和生命周期管理 |
| `deskpet/c_ui/renderer.py` | UiSpec 校验、组件构建和数据绑定 |
| `deskpet/c_ui/actions.py` | 收集输入、组装 UiAction、关联返回结果和错误提示 |
| `deskpet/c_ui/reminder.py` | 提醒卡、交付去重、可见绘制与回执 |
| `deskpet/c_ui/work_panel.py` | 目标、计时、阶段按钮和回顾编辑区 |
| `deskpet/c_ui/state_panel.py` | 有效状态、简明依据、纠正与清除入口 |
| `deskpet/work_sessions/service.py` | 工作段命令、版本校验、计时及事件 |
| `examples/m0/c-product.adapters.json` | C 组件与工作段服务的联调配置 |

首个工作段界面使用现有 mock 跑通交互，再接入 C 自己的服务。这样可分别定位界面问题和领域逻辑问题。正式接入配置拟为：

```json
{
  "ui_surface": "deskpet.c_ui.surface:create_surface",
  "work_sessions": "deskpet.work_sessions.service:factory"
}
```

工作段工厂签名保持 `factory(*, clock, emit)`，返回符合 WorkSessionService 端口的对象。C 只替换自己的工厂与组件，公共装配变更交由 A 协调。

## 4. 界面与用户流程

### 4.1 工作面板布局

面板先按四个区域组织：事项列表、当前工作段、工作回顾、状态入口。提醒卡可以同时承接多个不同交付，以独立事项和按钮区分，初版按接收顺序排列。最终堆叠方式与优先级规则在产品体验阶段确认。

事项时间使用用户可理解的日期和本地时区，例如「今天 17:00 到点提醒」「17:00–17:20 内提醒」「已延后至 17:30」。确认卡显示明确日期、时间、时区及强／柔性模式；时间含糊时让用户选择后再确认。任务版本、原始 JSON 和事件编号保留在联调诊断入口。

用户主动打开输入区时获取焦点。普通快照刷新保留正在输入的内容、光标和列表选择，不反复重建整个页面。收到提醒时遵循宿主展示路由，后台更新不激活其他窗口。

### 4.2 事项登记与提醒处理

1. 用户输入事项或通过结构化表单填写内容、提醒方式和时间。
2. 界面显示可编辑的确认卡；点击确认后提交动作，收到成功结果再显示已确认状态。
3. B 到期发送 DisplayCommand，C 展示相应提醒卡，真实绘制后提交展示回执。
4. 用户可选择「已完成」「稍后提醒」「修改」或「取消」。延后和修改提交前显示新的安排，具体 payload 沿用 B 的任务契约。
5. 操作处理中标记对应按钮；失败时显示原因并保留输入；成功后依据最新快照刷新事项和卡片。
6. 关闭卡片仅关闭表面，不将事项记为完成。关闭后的再次提醒节奏需与 B 及产品规则对齐。

强提醒与柔性提醒的调度均由 B 决定，C 不根据本地计时或推测的忙碌状态自行改变提醒安排。

### 4.3 工作段与回顾

用户填写目标和时长，可选择关联已有 task_id。开始后面板显示目标、剩余时长和当前阶段，提供暂停及结束；暂停后提供继续及结束。工作时间到期进入 break_due，显示「本轮时间到」和回顾入口。

结束前展示可编辑的成果与下一步字段，允许留空。用户确认后提交 session.end，保存 confirmed_outcomes 和 next_steps；收到成功结果后展示回顾。若提交失败，保留用户填写内容供重试。现有契约没有结束后编辑回顾的命令，首版在提交前完成确认；后续编辑能力另行定义。

切换应用和关闭面板不改变工作段状态。关联 task_id 只用于追踪关系，结束工作段不自动完成关联任务；任务完成仍需用户明确操作。

### 4.4 状态展示与纠正

常用入口显示「估计正在专注」「估计可打扰」「离开」「暂时无法判断」，并提供简明依据与更新时间。缺少有效信号时明确显示无法判断。

纠正表单收集状态、原因和持续时间，通过 `state.override` 提交；界面显示用户设置及截止时间，提供 `state.clear_override` 清除入口。基础估计、有效状态和纠正来源分开呈现，详细证据在诊断页展开。到期后采用管线发布的新快照，界面不自行延长纠正，也不因工作段已开始而自动提交用户标签。

## 5. UiSpec 动态渲染方案

首版严格采用当前公共模型支持的六类组件：

| 类型 | Qt 实现方向 | 主要处理 |
| --- | --- | --- |
| `text` | QLabel | 文本换行；按普通文本显示外部内容 |
| `card` | QFrame 与布局 | 显示卡片标题和绑定内容；首版使用现有扁平组件结构 |
| `text_input` | QLineEdit，必要时使用文本编辑控件 | 根据 component_id 保存输入草稿，通过 data_key 绑定表单字段 |
| `select` | QComboBox | 使用 options 限定选项，保留当前合法选择 |
| `button` | QPushButton | 绑定已注册 action_id，收集当前表单并提交 |
| `list` | QListWidget 或列表布局 | 展示绑定数据，按稳定标识更新选择项 |

处理顺序为：接收 UiSpec → 公共模型校验 → 构建组件映射 → 绑定 data → 注册动作 → 等待用户操作。renderer 作为独立模块，可先用固定样例测试；将上游 UiSpec 路由到嵌入组件的方式与 A 对齐，现有快照接口不被视为已经提供 UiSpec 推送。

组件使用 component_id 维护映射，表面使用 surface_id 与 surface_revision 标识。更新时尽量复用控件；当字段或表面已失效时清理旧绑定，保留仍适用的用户输入。当前模型没有嵌套子组件、任意样式脚本或自由布局协议，首版采用固定布局规则；扩展这些能力先修改公共协议。

每次用户动作生成 event_id，任务动作带 task_id、expected_task_version 和当前有效 surface_revision。表面版本沿用宿主约定，不在 renderer 中自行定义一套版本体系。工作段动作在 payload 中携带 session_id 与 expected_session_version。使用返回的 command_id 或 event_id 关联结果，仅更新对应操作的等待状态。

未知组件、非法数据或未注册动作显示可理解的失败提示，并保留诊断信息。界面不执行模型生成的 Python、JavaScript 或任意系统命令。

## 6. 提醒展示与一致性处理

### 6.1 交付与回执

C 维护 delivery_id 到卡片的映射，并保留 task_id、task_version 供清理与核对。同一交付重复到达时复用已有卡片；不同事项分别展示，不能相互覆盖。

展示回执按以下步骤处理：

1. `show_reminder` 接收宿主分配的有效请求并创建卡片。
2. 在卡片真实可见的 paintEvent 后安排 Qt 排队回调。
3. 回调再次检查组件仍存在、卡片可见、请求未被清理及 `context.can_report_display`。
4. 调用 `context.report_display(delivery_id)`；由 host 补齐任务、版本、时间和 native/offscreen 来源。
5. 该方法返回 true 只表示回执已送入队列，最终入账由服务结果和交付事件确认。

创建控件、调用 show_reminder、隐藏绘制或截图不计为实际展示。失败或拒绝使用公共 ErrorCode 报告，不能用默认卡片掩盖 C 组件错误。

### 6.2 版本变化与迟到结果

| 情况 | 界面处理 |
| --- | --- |
| 同一 delivery_id 重送 | 复用卡片，避免重复创建和重复有效回执 |
| 用户取消或任务版本改变 | 清理失效卡片、旧动作绑定和待执行回调，按新快照显示当前事项 |
| 旧按钮晚到 | 接受宿主／服务的过期拒绝，提示内容已更新并刷新 |
| 用户连续点击同一动作 | 操作等待期间限制重复提交；仍由服务命令去重与版本校验兜底 |
| 某一动作结果晚于新快照 | 仅清理对应等待状态，不能用旧结果覆盖新快照或重开卡片 |
| 卡片销毁或宿主关闭 | 停止定时回调、断开相关连接，不再提交动作和回执 |

## 7. 工作段服务设计

### 7.1 端口与状态迁移

实现 `apply`、`get`、`list_sessions` 和 `pump`，输入输出复用公共 SessionCommand、SessionResult 与 WorkSession。服务在单一领域线程内维护记录，读取快照的界面不直接调用服务实例。

| 当前状态 | 输入／事件 | 下一状态 | 关键行为 |
| --- | --- | --- | --- |
| 不存在 | start，expected_version=0 | focusing | 校验目标及正数时长，建立 v1 和到期时刻 |
| focusing | pause | paused | 固定剩余时长，清除当前到期安排，版本递增 |
| paused | resume | focusing | 用保留时长计算新到期时刻，版本递增 |
| focusing | pump 检测到期 | break_due | 剩余时间为 0，版本递增，发出一次到期事件 |
| focusing／paused／break_due | end | ended | 清除到期安排，保存确认成果和下一步，版本递增 |
| ended 或其他非法状态 | 不适用的操作 | 保持原状态 | 返回契约规定的拒绝结果 |

首版沿用 mock 的状态迁移及版本行为。对于暂停与到期同时发生的边界，先 pump 再处理命令；界面根据最新版本刷新，避免仍显示可暂停的旧状态。

### 7.2 计时、版本与重复命令

- 使用注入 Clock 的单调时间计算运行期间的剩余时长，墙上时间用于 phase_due_at 的展示与事件时间。
- focusing 时按 `max(0, due_monotonic - now_monotonic)` 更新剩余秒数；paused 时保留数值。Qt 刷新频率不影响领域计时。
- 普通计时读取不增加版本；开始、暂停、继续、到期和结束等语义迁移增加版本。
- 按 command_id 记录命令及结果；相同 ID、相同内容返回 duplicate，内容冲突按现有语义拒绝。版本不符或状态不允许时保留当前记录。
- 结束只保存用户明确提交的成果，不根据应用使用记录生成已完成结论。

首版服务可保持进程内存实现以验证语义。跨进程不能直接复用单调时钟数值；工作段持久化、睡眠期间是否计时及错过阶段的处理需要单独方案和恢复测试，不能以本轮计时测试代替。

### 7.3 完整番茄钟的后续方案

基础闭环稳定后，再提出工作／休息阶段、延长、开始下一轮和自动建议的协议扩展。拟优先采用用户手动开始、到期后选择下一步的流程；工作／休息时长作为可配置值。自动模式需要明确启用入口、触发条件、关闭后的清理和误判处理，并与 A 的观察状态及策略协作。

这些流程需要公共状态与动作支持，不能仅靠 UI 文案或私有字段模拟。协议确认前，break_due 只表示本轮工作时间已到，不宣称已经进入完整休息周期。

## 8. 与 A、B、D 的协作

| 对接方 | C 需要对齐的输入 | C 提供的结果 | 联调重点 |
| --- | --- | --- | --- |
| A | SurfaceContext、UiSpec 来源与路由、动作白名单、观察帧、公共 Clock | ui_surface 工厂、动作提交、状态纠正界面 | 版本语义、线程边界、组件生命周期、桌宠共享宿主 |
| B | TaskView、CommandResult、DisplayCommand、任务动作 payload | UiAction、展示／失败回执、交互问题证据 | 确认到展示再到完成、取消竞争、延后及卡片清理 |
| D | 事件字段、场景及报告口径 | 工作段命令与迁移事件、界面操作来源、截图和 trace | event_id／command_id／delivery_id／session_id 的关联 |

工作段事件沿用现有 `session.applied`、`session.rejected`、`session.duplicate` 和 `session.break_due` 等口径，新增事件先与 D 对齐。任务与展示事实由所属服务发出，C 不自行重复记为成功。手工操作、自动 smoke 和脚本回放保留各自来源，模拟结果不计入真实人工效果。

## 9. 分阶段实施与交付

以里程碑安排先后，具体时间在团队明确总截止时间后补充。

| 阶段 | 实施内容 | 交付物与退出条件 |
| --- | --- | --- |
| P0：接入准备 | 阅读契约和样例，运行基线，确认动作 payload 和 UiSpec 接入方式 | 基线结果、C 模块骨架及适配配置；可在联调台加载 C 页 |
| P1：工作段闭环 | 先接 mock 实现面板，再替换为 C 的工作段服务；完成开始、暂停、继续、结束与回顾 | 两页同一 session_id、版本和剩余时间；暂停不减时；确认回顾可查看 |
| P2：提醒闭环 | 接入真实 DisplayCommand 和任务动作，实现去重、可见回执、清理与错误反馈 | 确认→到期→展示→完成／延后可走通；取消后旧结果不重开卡 |
| P3：动态界面与状态 | 实现六类组件、动作绑定、草稿保留、状态查看与纠正 | 固定 UiSpec 样例及上游联调均可操作；不支持内容有明确提示 |
| P4：产品体验与验收 | 完善布局、中文时间、焦点、多个提醒及异常提示；与 A 讨论桌宠入口 | 原生演示、截图和 trace；记录平台限制；列出后续番茄钟扩展项 |

每阶段以可运行的纵向闭环提交小范围 PR，说明本次行为、验证结果和剩余依赖。先固定数据与脚本验证，再接真实上游；桌宠动画与样式完善放在核心交互稳定之后。

P0 的实际入口、运行方式与实现边界见 [C 接入准备](../c-p0.md)。P1 见 [C 工作段闭环](../c-p1.md)，P2 见 [C 提醒闭环](../c-p2.md)，P3 见 [C 动态界面与状态](../c-p3.md)。P4 已改善分区布局、中文时间、焦点与多提醒显示，并以复用既有素材／动画的桌宠入口打开同一后端，见 [C 体验完善与桌宠入口](../c-p4.md)。旧桌宠完整自主行为、通用上游 UiSpec 推送、真实模型界面、完整番茄钟与恢复能力不包含在这些已验收结果中。

## 10. 验证与验收标准

### 10.1 逻辑及集成检查

实现时优先复用现有测试和 fixtures，新增测试集中覆盖状态边界、竞态及渲染生命周期：

| 场景 | 通过条件 |
| --- | --- |
| 暂停与继续 | 暂停期间快进时间不减少 remaining_s，继续后按剩余时间到期 |
| 到期边界 | 多次 pump 只发生一次 break_due 迁移；到期后的旧命令被正确拒绝 |
| 重复与冲突命令 | 同 ID 同内容不重复迁移，版本冲突不覆盖新状态 |
| 用户回顾 | 成果和下一步与用户确认值一致；结束不自动完成关联任务 |
| 动态组件 | 六类组件按协议显示，非法类型／动作被拒绝，刷新保留合法输入 |
| 重复提醒与取消 | 同一交付只保留一张卡，取消后旧回调不再生成成功展示 |
| 展示证据 | 隐藏、截图、销毁及过期请求不产生有效成功回执 |
| 状态纠正 | 有效期内显示纠正，清除／到期后展示管线给出的有效状态 |
| 多入口与多个提醒 | 两页状态一致，不同提醒互不覆盖，操作只影响对应事项 |

完成对应实现后，运行既有命令核对基线；文档编写阶段不将这些检查标记为已执行：

```sh
uv run python -m pytest -q tests/m0/test_ui_surface.py tests/m0/test_work_runtime.py
uv run python -m deskpet.m0 replay --suite m0 --output output/m0/c-replay
uv run python -m deskpet.m0 replay --scenario session-pause --output output/m0/c-session-pause
```

新增 C 模块测试随实现纳入相应测试目录。离线 replay 验证服务与事件，renderer 的控件行为另用 Qt 集成测试和原生界面核验。

### 10.2 原生界面与交付证据

先运行仓库现有嵌入样例熟悉联调，再使用实际创建的 C 配置运行自己的组件：

```sh
uv run python -m deskpet.m0 gui --profile scenario --adapters examples/m0/c-ui.adapters.json --output output/m0/c-baseline
# C 模块及配置实现后：
uv run python -m deskpet.m0 gui --profile scenario --adapters examples/m0/c-product.adapters.json --output output/m0/c-product
```

在真实、可见的 Qt 窗口核对：中文可读、按钮可点、输入不被刷新覆盖；暂停／继续和回顾符合预期；强提醒和柔性提醒显示的时间安排清楚；普通后台更新不抢焦点；取消、延后及编辑后旧卡不会恢复。

每轮保留实际源码版本、适配配置、测试结果、场景报告、原始 trace 和截图。用 delivery_id 关联请求与回执，用 session_id 关联工作段，用 command_id 关联操作结果。offscreen 和模拟回执用于逻辑检查，原生展示需核对 native 来源；Windows 实机结果单独记录，未执行项标为待验收。

## 11. 风险、取舍与待确认项

| 问题 | 处理方案 |
| --- | --- |
| 上游 UiSpec 或公共协议尚未冻结 | 用现有模型和固定样例先开发，正式路由与新增字段由 A 协调 |
| 动态重绘打断输入或丢失焦点 | 按稳定组件 ID 更新，保留输入草稿；表面失效时明确提示 |
| 多线程调用和关闭后回调 | 统一经过宿主队列，组件销毁时停止回调并清理连接 |
| 将显示成功误记为任务完成 | 展示回执与完成动作分别处理，以服务事实事件为准 |
| 番茄钟扩展超出现有四状态 | 先交付手动工作段，休息、延长及自动模式另行定义公共协议 |
| 持久化与睡眠恢复语义不完整 | 明确首版内存边界，后续与相关服务负责人约定恢复策略 |
| 外观工作影响核心交付 | 先完成 P1／P2 的可操作闭环，再完善像素风及桌宠整合 |

需要团队进一步确认的产品项包括：小猫打开助手的手势、关闭提醒卡后的后续策略、多个提醒的最终排序、工作／休息默认时长、自动模式采用建议还是直接启动，以及睡眠／重启后的工作段恢复规则。

该方案延续现有共享后端和单一展示路由，便于 C 独立开发并让 A、B、D 使用同一套场景核对。代价是首版布局受当前 UiSpec 能力约束，完整番茄钟与桌宠外观整合分后续步骤交付。
